# Human Approval Matrix

This matrix classifies every Team operation into one of four classes:

- **系统自动 (auto)** — scripts/tools act on their own inside established rules.
- **AI 可建议不可决定 (suggest-only)** — the AI may propose; execution requires human approval.
- **必须用户确认 (confirm-each)** — one human confirmation per occurrence.
- **永不自动 (never-auto)** — no automated path may perform it; only a direct human command.

The matrix is normative for every Team seat and every bootstrap tool. `team doctor`
verifies that every row id below exists; a missing row fails the check.

## Bootstrap governance clause (一把手条款落地)

- The Leader makes reversible technical coordination decisions **inside the
  user-approved objective and boundaries** (auto, AP-06).
- Substantive changes to objective, scope, or acceptance criteria are
  suggestions only; only the current user decides them (suggest-only, AP-08).
- A completion claim means only "local evidence satisfies the task's
  acceptance criteria". User acceptance is a separate, single act reserved
  for the current user (confirm-each, AP-15). `worker_done` is not acceptance.

## Enforcement mapping

| Row | Enforcing tool | Fail-closed behavior |
|---|---|---|
| AP-02 | `message inject` | Rejects agent-supplied tool fields, exit 9 |
| AP-03/AP-09/AP-21 | `provision run` / `deprovision` | paths digest required; dirty worktree refused, exit 8 |
| AP-10/AP-22 | `team_roster.py` | Validator rejects non-schema writes; `roster-update` refuses rotation without generation increment |
| AP-11 | `adopt-team-charter apply` | confirm digest required; backups mandatory; postcondition verified |
| AP-13 | `message keys` | Never overwrites existing keys; rotation refused by `roster-update` |
| AP-14 | `message verify` | Enforced by default; no downgrade switch exists in the tooling |
| AP-16 | quickstart/provision | No push/deploy path exists in any team tool |
| AP-19 | quickstart | Claude seats require exactly `--permission-mode auto`; any other mode fails closed before terminal creation |

## Change procedure (AP-12)

1. Propose the change with a unique Rule-Change-ID, objective, trigger,
   affected seats/tools, compatibility impact, and checkable acceptance.
2. The current user reviews and confirms the change explicitly.
3. The change lands in its own commit; the doctor matrix check re-passes
   before the next operation.
